## 1. 背景与目标

### 1.1 问题

跨 Windows / macOS / Linux 时，局域网传文件常依赖 U 盘、网盘或平台锁定方案（如 AirDrop）。需要一款：

- 无云、无账号
- 自动发现对等设备
- 可互传文件/文件夹
- 可落在本 monorepo `app_desktop/` 下，作为桌面端弹药与接单白标雏形

### 1.2 核心目标（V1）

1. 在同一局域网内自动列出在线的 LanDrop 设备  
2. 向选定设备发送一个或多个文件，或整个文件夹  
3. 接收方确认后写入本地默认下载目录（可配置）  
4. 展示传输进度，支持取消  
5. 组播失败时可用 IP 或二维码手动连接  

### 1.3 非目标（明确不做）

| 项 | 说明 |
|----|------|
| 手机端 | V1 不做 iOS/Android |
| 与 LocalSend 互通 | 不实现官方协议兼容 |
| 浏览器接收页 | 对端必须装 App |
| 断点续传 / 多接收会话并行 | 后续迭代 |
| 云同步、账号、好友系统 | 不做 |
| 全网 ARP/端口扫描列「所有电脑」 | 不做；只列同款 App |
| V1 完整白标流水线 | 仅结构预留 |

## 2. 用户与场景

### 2.1 用户

- 自己：多台电脑互传（开发机 ↔ 测试机）  
- 接单演示 / 未来白标客户：办公室或展会内网互传  

### 2.2 主路径

1. 两端安装并启动 LanDrop（托盘常驻）  
2. 设备列表出现对方（显示名称、系统、指纹缩写）  
3. 发送方选文件/文件夹 → 选设备 → 发送  
4. 接收方弹窗确认（文件名、大小、来源设备）→ 接受/拒绝  
5. 传输中双方看进度；任一方可取消  

### 2.3 兜底路径

- 列表为空：发送方输入对方 IP:端口，或扫描对方展示的二维码（内含连接信息）

## 4. 技术方案（调研结论 + 约定）

### 4.1 方案对比（为何自研精简协议 + Electron）

| 方案 | 优点 | 缺点 | V1 结论 |
|------|------|------|---------|
| 直接用 LocalSend | 零开发、含手机 | 无自有品牌/白标控制 | 不用作产品本体 |
| 兼容 LocalSend 协议 | 生态互通 | 跟协议演进；品牌/端口难白标 | 不做 |
| Electron 自研 | 对齐 `teach-hub-desktop`；Node 网络成熟 | 安装包偏大 | **采用** |
| Tauri 自研 | 体积小 | 本仓无先例；工期风险 | 预留迁移，不做 V1 |

### 4.2 推荐架构

```
┌─────────────────────────────────────────┐
│  Renderer (React + Vite)                │
│  设备列表 / 发送 / 接收确认 / 设置 / 托盘提示 │
└─────────────────┬───────────────────────┘
                  │ preload IPC
┌─────────────────▼───────────────────────┐
│  Electron Main                          │
│  ├─ discovery/   UDP 组播 + 设备表        │
│  ├─ transfer/    HTTPS 服务 + 客户端上传   │
│  ├─ cert/        自签证书与指纹           │
│  └─ settings/    网卡、端口、下载目录、显示名 │
└─────────────────────────────────────────┘
```

协议层（`discovery` + `transfer` + `cert`）保持 **无 Electron 依赖的纯 TS 模块边界**，便于日后抽到 `sa2kit` 或换 Tauri 壳。

### 4.3 协议草图（实现阶段可细化 ADR）

**发现（默认）**

- UDP 组播宣告 + 监听（地址/端口在实现时选定并写入设置默认值；避免与 LocalSend 默认 `53317` 冲突，便于同机并存）  
- 载荷：JSON（`deviceId`, `displayName`, `port`, `fingerprint`, `os`, `protocolVersion`）  
- 存活：定期宣告；超时未更新则从列表移除  

**传输**

- 接收方起本地 HTTPS 服务  
- 发送方：`prepare`（元数据）→ 等待接受/拒绝 → 按文件流式 `upload`（文件夹用相对路径）  
- 单接收会话锁；取消有明确信令  

**安全**

- 每设备持久化自签证书；指纹 = 证书哈希（展示给用户）  
- V1 不做 PIN 信任列表（列为 V1.1）  

### 4.4 仓库与工程约定

| 项 | 约定 |
|----|------|
| 父仓路径 | `app_desktop/lan-drop` |
| 形态 | git submodule（独立仓，命名建议 `profile-v1-lan-drop`） |
| 栈 | Electron + Vite + React + TypeScript（对齐 teach-hub-desktop） |
| 依赖 sa2kit | 可选 UI/工具；**网络协议 V1 不进 sa2kit** |
| 包管理 | 纳入 pnpm workspace `app_desktop/*`；根脚本 `dev:lan-drop`（实施时加） |

## 5. 非功能需求

| 类别 | 要求 |
|------|------|
| 性能 | 千兆局域网下大文件应接近磁盘/网卡瓶颈；UI 不因传输卡死 |
| 可靠性 | 对端掉线、拒绝、取消、磁盘满要有明确错误提示 |
| 安全 | 默认不自动接收；传输加密；不上传任何数据到公网 |
| 兼容 | Win 10+、近期 macOS、主流 Linux（至少 AppImage 或等价） |
| 可维护 | 协议模块可单测；主进程与渲染进程边界清晰 |
| 白标预留 | 应用显示名、图标、包名集中配置，无硬编码散落 |

## 6. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 路由器 AP 隔离 / 防火墙拦组播 | 帮助文案 + IP/二维码兜底；文档写明需放行 UDP/TCP 端口 |
| 多网卡 / VPN 选错 | 自动启发式 + 手动选网卡 |
| Electron 体积与自动更新 | V1 可先手动发 GitHub Release；更新策略后补 |
| 文件夹符号链接 / 权限文件 | V1 跳过无法读取的项并记日志/提示 |
| 同机多实例 | 单实例锁；端口占用提示 |

## 9. 验收标准（V1）

1. 两台不同 OS 的机器（至少两两组合中的一种：Win↔Mac 或 Mac↔Linux 等）同局域网互可见  
2. 可传多个文件与一个含嵌套的文件夹，内容与相对路径正确  
3. 拒绝与取消行为符合预期，无残留半文件或会话死锁（或半文件有明确清理策略）  
4. 关闭主窗口后仍能弹出接收确认（托盘存活）  
5. 关闭组播或跨网段时，IP/二维码仍能完成一次传输  
6. 设置中切换网卡后，列表与本机展示 IP 与所选一致
