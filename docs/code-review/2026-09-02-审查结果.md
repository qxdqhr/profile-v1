## 0. 一句话结论

这是一个 **「个人平台 + 实验田 + 多端产品」叠在同一仓、同一 Postgres、同一 CI 网关上的超级单体**。领域拆分（`*-core` + 子应用）已经开始，但 **拆应用没有拆数据、没有拆鉴权面、没有拆构建图**；主站仍是厨房水槽；镜像与 CI 有多处复制粘贴缺陷，可能长期靠「晋升旧 tag」掩盖。安全和工程卫生问题比「目录看起来像 monorepo」更紧急。

## 1. 从目录还原的实际架构

```
profile-v1/                          ← pnpm workspace 成员（根包自己也是 package）
├── app_web/web          :3000       主站 Next 16（实验田 + 约 25 个模块 + 150 条 API）
├── app_web/calendar     :3001 /calendar
├── app_web/teach-hub    :3002 /teach-hub
├── app_web/showmasterpiece :3003 /showmasterpiece
├── app_web/money-research  :3004 /money-research
├── app_web/node-notes      :3005 /node-notes
├── app_mobile/*             git submodule + workspace
├── app_desktop/*            git submodule + workspace
├── app_games/*              20 个 Godot git submodule（不在 pnpm workspace）
├── app_wordpress/holt       git submodule（PHP 旁路）
├── packages/{auth,config,db,ui,*-core,sa2kit-*}
├── deploy/                  网关 compose + 每游戏一个 nginx 容器
└── drizzle/                 根目录 60+ SQL 迁移（全平台一张库）
```

生产形态（`deploy/docker-compose.gateway.yml`）：**同域 nginx 反代** → 6 个 Next 容器 + WordPress/MariaDB + **约 19 个独立游戏 nginx 容器**。Postgres 不在 compose 内，通过 `DATABASE_URL` / `host.docker.internal` 共用宿主机库。

鉴权：Better Auth，封装在 `@profile/auth`；**web / calendar / teach-hub / showmasterpiece / node-notes 各挂一份** `app/api/auth/[...all]`。客户端 `baseURL` 用 `window.location.origin`，生产上会打到主站 `/api/auth`。

数据：`@profile/db` 聚合 **所有** 领域 schema（含 `*-core`、sa2kit 的 file/festivalCard、主站模块表），Drizzle 出口在仓库根。

## 2. 问题清单（按严重度）

### P0 — 安全 / 可能直接出事故

#### P0-1 无全局鉴权面，大量 API 裸奔

仓库内 **没有** `middleware.ts`。Session 校验是各 `route.ts` 自行调用 `getApiSessionUser`。主站 `app/api` 下约 **150** 个 `route.ts`，能搜到 session 调用的大约十几个文件。

已核实的公开面：

| 路径 | 问题 |
|------|------|
| `/api/proxy-image?url=` | 任意 URL `fetch`，无协议/内网/元数据地址过滤 → **SSRF** |
| `/api/examples/oss/list` | 无登录，可列 OSS |
| `/api/skill-manager/skills` | GET 无 session |
| `/api/test-env` | 回传 auth URL、sms provider、OSS bucket |
| `/api/test-route` | 调试 ping，进生产镜像 |
| `next.config.ts` `headers()` | **全路径** `Access-Control-Allow-Origin: *` |

`ideaList` 等新模块有按用户鉴权，说明团队知道怎么做，但没有强制闸门，旧实验 API 继续暴露。

#### P0-2 生产库地址进 Git，且像是对公网开放

`.idea/dataSources.xml` 被跟踪，含：

- `jdbc:postgresql://qhr062.top:5432/exam_system`
- `jdbc:postgresql://qhr062.top:5433/lyricnote_prod`

没有密码，但等于公开了生产 Postgres 主机与库名。若 5432/5433 确实对公网监听，这是独立的基础设施事故。

#### P0-3 调试 / 示例路由随主站进生产

仍在 `app_web/web/src/app` 里、会被 `next build` 打进镜像：

- `api/mikutap/background-music/debug`
- `api/vocaloid-booth-test`、页面 `vocaloid-booth-test`
- `api/examples/**`（OSS / QQ 机器人 / 日历 mock）
- `(pages)/examples/**`、`(pages)/timestamp`、`(pages)/test-route`

实验田可以存在，但 **API 与页面没有生产开关**。

#### P0-4 WordPress compose 带弱口令默认值

```yaml
MARIADB_ROOT_PASSWORD: ${MARIADB_ROOT_PASSWORD:-change-me-root}
WORDPRESS_DB_PASSWORD: ${WORDPRESS_DB_PASSWORD:-change-me-wp}
```

Secrets 漏配时会用这些值启动，且仓库写明了默认值。

### P1 — 架构边界失败 / 构建可能是坏的

#### P1-1 子应用 Dockerfile 复制粘贴，按字面会构建失败

`app_web/calendar|teach-hub|showmasterpiece|node-notes/Dockerfile` 共同问题：

1. **`COPY npm ./npm`**：仓库 **没有** `npm/` 目录。Docker `COPY` 源不存在会失败。根 `dockerfile` 与 `app_web/web/Dockerfile` 同样如此。
2. **runner 阶段 `chown -R nextjs:nodejs web`**：该阶段根本没有 `web` 目录（只 `mkdir` 了 `app_web/<app>/.next-*`）。
3. 注释仍写「`@profile/db` schema 仍聚合 `app_web/web` 模块表」，因此继续 `COPY app_web/web/src/modules`。实际 `packages/db/src/schema/index.ts` 已改从 `*-core` 与 `packages/db/src/schema/*` 聚合，**这条 COPY 是过期耦合**。

CI 对未改动的应用会「向前 50 个 run 晋升旧镜像」。这能让 **坏 Dockerfile 长期不被执行，现网继续跑旧镜像**，直到某次路径命中才爆。

#### P1-2 `.dockerignore` 几乎为空

根 `.dockerignore` 仅 1 字节。构建上下文会带上 `node_modules`、`.git`、`.next`、游戏 submodule、文档等。即使 `COPY` 是白名单，上下文传输和缓存仍会很差，也增加误 `COPY .` 的风险。

#### P1-3 拆了应用，没拆数据库，也没拆构建图

`@profile/db` 是上帝包：

- 依赖：`calendar-core` + `teach-hub-core` + `showmasterpiece-core` + `node-notes-core` + `auth` + `sa2kit`
- schema 出口把所有业务表打进 **同一个 Drizzle 客户端**
- 任意子应用 `import '@profile/db'` 都会拉进全平台表

后果：

- calendar 镜像构建仍可能因 showmasterpiece schema 挂掉
- `prodb:push` / `devdb:push` 一次对准整库
- 迁移爆炸半径 = 全站
- `deploy/ensure-calendar-schema.sh`、`ensure-node-notes-schema.sh` 等补丁脚本说明 **正规迁移不被信任**

#### P1-4 `@profile/auth` ↔ `@profile/db` 循环依赖

- `packages/auth/package.json` 依赖 `@profile/db`（server 里 `import { db } from '@profile/db'`）
- `packages/db/package.json` 依赖 `@profile/auth`，**源码里没有任何 `@profile/auth` import**

这是幽灵环。pnpm 能转，但类型检查、打包顺序、未来拆包都会踩。根因：auth schema 放在 db，auth 运行时又握着 db 单例。

另外 `packages/auth/src/server.ts`：

```ts
export const auth = getAuth();
```

模块加载即连库、读配置。Docker build / 某些 CI 路径只要 import 到这个模块就会在没有 `DATABASE_URL` 时炸掉，或连上错误的库。

#### P1-5 领域 cutover 不彻底，双挂载仍在

| 领域 | 独立应用 | 主站残留 |
|------|----------|----------|
| node-notes | `app_web/node-notes` + `/api` 在 core | 主站仍 `app/api/node-notes/*` 再导出；页面仍挂 `/testField/nodeNotes`；`NEXT_PUBLIC_NODE_NOTES_EMBED_PATH` 指向实验田 |
| showmasterpiece | 独立应用 | `src/modules/showmasterpiece` 薄再导出；`next.config.ts` 仍给 **已不存在的** `/api/showmasterpiece/bookings/admin` 写缓存头 |
| calendar | 独立应用 | 主站 `api/examples/calendar` mock 仍在；`calendar.zip` 仍进 Git |
| festivalCard | 已在 sa2kit | 主站仍挂 `/api/festivalCard` |

架构门禁 `scripts/check-architecture-gate.mjs` **只禁 3 条路径**（web 的 showmasterpiece API、calendar/teach-hub 的 ai API）。node-notes 双挂、各子应用自己的 `/api/auth`、examples 全部不管。CI **也不跑这个 gate**。

#### P1-6 五个进程各挂一套 Better Auth

生产 cookie 客户端打 `origin + /api/auth`（主站），但每个子应用 `basePath` 下还有 `/api/auth`。同一 `secret` + 同一库可以校验 session，也可以：

- 登录/回调打到错误的 basePath
- trailingSlash（子应用开了，主站没开）导致 308 丢 cookie
- 子应用与主站 `trustedOrigins` 漂移

这不是「多端 SSO 设计」，是 **复制粘贴出来的第二鉴权面**。

#### P1-7 `ignoreBuildErrors: true`

- `app_web/node-notes/next.config.ts`
- `app_web/money-research/next.config.ts`

类型错误可以进生产镜像。与 web/calendar/teach-hub/showmasterpiece 的 `false` 不一致。

### P2 — 工程卫生、运维复杂度、历史债

#### P2-1 主站是厨房水槽

`@profile/web` 同时依赖：Phaser、Pixi、Three、MMD、Tesseract、Transformers、Monaco、imgly 抠图、七牛、阿里云 OSS、SWR、Zustand、两套 DnD（`@dnd-kit` + `react-beautiful-dnd`）、三套 PG 客户端倾向（`postgres` / `pg` / `@neondatabase/serverless`）。

25 个 `src/modules`，实验田 + 客户产品 + 游戏 + AI + 票务监控挤在一个 Next 进程。结果：

- 冷启动 / 镜像体积 / webpack 配置（`--webpack` + 空 `turbopack: {}`）都为主站最重路径买单
- `images.unoptimized: true` 全站关闭优化
- `viewport.userScalable: false` 伤无障碍

`@profile/ui` 名不副实：只有 Tailwind preset，组件在 sa2kit-ui；根目录仍留 shadcn `components.json`，web 还装着一堆 `@radix-ui/*`。

#### P2-2 根目录仍是「旧 Next 单体」的残骸

跟踪或未忽略的残留：

| 路径 | 说明 |
|------|------|
| 根 `dockerfile` | 注释写兼容旧命令，与 `app_web/web/Dockerfile` 重复 |
| `components.json` / `fix-sa2kit-types.js` / `manual_cleanup.sql` / `push_db.exp` | 一次性脚本 |
| `app_web/web/src/components.zip`、`modules/calendar.zip`、`app/(pages)/testField/(cyhj).zip` | 二进制进 Git |
| `app_web/web/src/db/*` | `@deprecated` 再导出，但 `exam-service.ts` 仍是活代码 |
| 根 `tsconfig.json` | paths 只覆盖部分包；`include` 几乎只指向 web |
| 根 `package.json` | workspace 含 `'.'`，根包还依赖 drizzle/sa2kit，脚本 70+ 条全堆在根上 |
| `pnpm-workspace.yaml` | 含 `app_mobile/*`、`app_desktop/*`，这两个是 **submodule**；不 recursive clone 则 install 失败 |

#### P2-3 Drizzle 迁移目录不干净

- 磁盘 63 个 SQL，journal 60 条
- **不在 journal 的孤儿**：`0010_organic_lifeguard.sql`、`0051_add_home_tab_config.sql`、`0052_remove_showmaster_events.sql`
- 序号冲突：`0010_*`、`0051_*`、`0052_*` 各两份
- `drizzle.config.ts` 用 `dotenv` + `DATABASE_URL`，运行时用 YAML `AppConfig` —— 两套配置源
- 同时提供 `*db:push` 与 `*db:migrate`；生产脚本偏向 **push**，和迁移链并存最容易漂库

#### P2-4 游戏旁路：一游戏一容器

compose 里约 19 个 `game_*` 服务，每个都是独立 `nginx:alpine` + 自己的 `nginx.conf`。平台 nginx 还 `depends_on` 它们全部。

代价：内存、启动时间、故障面。静态资源完全可以 **一个 nginx + 多 location**，或直接由平台 nginx `alias`。

`app_games` 有 **20 个 submodule**，URL 混用 HTTPS 与 `git@`；`diner-dash` 指向另一个命名的仓库 `diner-dash-clone`。当前工作区 `git submodule status` 全部为 `-`（未初始化记录），clone 体验很差。

#### P2-5 CI 是部署脚本，不是质量闸门

`.github/workflows/docker-build-push.yml` 在 main 上：改路径 → 构建镜像 → scp 到 **root@服务器** → `docker compose up`。

缺失：

- PR 上的 `lint` / `pnpm gate` / 类型检查（除了镜像构建碰巧编译）
- 自动化测试：全仓 **0** 个 `*.test.*` / `*.spec.*`
- `turbo.json` 只有 build/lint/dev，没有 test；根 `lint` 只 filter `@profile/web`
- 构建 job **不** `submodules: recursive`（changes job 有）
- 部署：`StrictHostKeyChecking=no`，私钥写 `/tmp/ssh_key`，远端路径 `/root/profile-v1`
- 另有一串「紧急修复」workflow：`gateway-fix.yml`、`gateway-fix-only.yml`、`remote-fix-now.yml`、`cleanup-server-disk.yml`、`reset-holt-wp-password.yml` —— 运维入口散落，权限面很大

镜像 tag = `github.run_number`，未变更应用靠回溯 50 个 tag 晋升。语义版本、digest pin、回滚策略都没有。

#### P2-6 配置与密钥

正向：SOPS + age（`config/production.enc.yaml` 进 Git，私钥 `config/keys/` gitignore）。

风险：

- 本地明文 `app.config.local.yaml` / `app.config.production.plain.yaml` 依赖开发者纪律
- Next `env` 把 `NEXT_PUBLIC_*` 打进客户端包；子应用用 YAML 的 `auth.publicUrl` 做 `NEXT_PUBLIC_APP_URL`，配错会把生产 URL 烘焙进错误环境
- 根脚本 `prodb:*` 可从开发机对生产库 push / seed / 改用户，没有环境隔离护栏

#### P2-7 运行时观测性几乎没有

compose 里 **只有 MariaDB** 有 healthcheck。6 个 Next 与 19 个游戏 nginx 均无。平台 nginx `depends_on` 不带 `condition: service_healthy`。进程挂了靠 `restart: unless-stopped`，网关会继续把流量打到死 upstream。

## 3. 依赖与分层（示意）

```
浏览器
  └─ nginx :80
       ├─ /                → web:3000     （实验田 + 主站模块 + 仍挂 node-notes API）
       ├─ /calendar        → calendar     （仍 COPY 主站 modules）
       ├─ /teach-hub       → teach-hub
       ├─ /showmasterpiece → showmasterpiece
       ├─ /money-research  → money-research  （ignoreBuildErrors）
       ├─ /node-notes      → node-notes      （与主站 /testField/nodeNotes 双活）
       ├─ /wp/holt         → wordpress + mariadb
       └─ /games/<slug>    → 每游戏一个 nginx

所有 Next ──同一 DATABASE_URL──► 宿主机 Postgres
所有 Next ──@profile/auth + 同一 secret──► user/session 表
@profile/db ──聚合──► 全部 schema
```

应当变成的方向（不在本次实现，仅作对照）：

- **一个鉴权面**（仅 web 或独立 auth 服务），子应用只校验 session
- **按域拆 schema / 迁移**（至少 calendar / teach-hub / 主站实验表分离），禁止 db 包依赖 auth
- **主站实验 API 默认拒绝未登录 + 生产禁用 examples/debug**
- **静态游戏合并进平台 nginx**
- **Dockerfile 以 web 为唯一模板，禁止 COPY 不存在的路径**
